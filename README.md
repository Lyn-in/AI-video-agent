# AI视频Agent平台

把「持续自我迭代地生成高质量提示词」做成一条可管理的流水线。
平台不生成视频，平台生产的是可执行的高质量提示词 + 可审可溯的生产流程。

**当前进度：M0-M6 七个里程碑全部完成。29 个回归测试。**

商业化前的缺口见 `商业化就绪度审查.md`（鉴权、CSRF、多租户、成本护栏为 P0/P1）。

---

## 快速开始

```bash
cd av-agent
python3 cli/avctl.py init      # 初始化数据库与目录
python3 cli/avctl.py smoke     # M0 验收自检，应全绿
```

零外部依赖，Python 3.11+ 直接跑。真实调用模型时才需要密钥：

```bash
cp config/secrets.env.example config/secrets.env   # 填入 key
source config/secrets.env
```

没有密钥时给任何 `run` 命令加 `--dry-run`，会用占位产物跑通全流程 ——
改引擎逻辑时不必烧 token。

## M0 交付了什么

### 1. 五份产物契约（`core/contracts/`）

平台的接口协议，早于所有 skill 存在。

| 契约 | 生产者 | 消费者 |
|---|---|---|
| story_file 故事档案 | 作家 | 编剧、导演匹配器 |
| screenplay 剧本 | 编剧 | 选角、场务、分镜 |
| character_board 角色板 | 选角 | 分镜、用户 |
| location_board 场景板 | 场务 | 分镜、用户 |
| shotlist 分镜表 | 分镜 | 用户 |

```bash
python3 cli/avctl.py contract list
python3 cli/avctl.py contract show screenplay
```

**契约里内置了三条执法**，不是君子协定：

- **编剧禁区**：剧本的 beats 文本里出现「镜头/特写/推近/转场/打光」等术语直接判越权。
  职责边界写在 SKILL.md 里只是嘴上说，写进校验器才是真的。
- **锚定描述长度下限**：角色板与场景板的 anchor_description 短于 60 字直接打回。
  锚定描述不够厚，跨镜头一致性必崩。
- **引用完整性**：分镜表里的 character_ids / location_id 必须在角色板/场景板中真实存在。
  这是「分镜不得自己发明人物长相和场景样貌」的机器化执法。

### 2. Skill 资产包规范（`core/skillkit/`）

任何 skill —— 包括未来新增的 —— 不符合规范，平台拒收。

```
skill包/
├── SKILL.md        五个强制章节，且每章不能只有模板注释
├── manifest.json   类型/团队/版本/输入输出契约/模型绑定/references 配置
├── references/     私有学习库，支持 S/A/N 分级（范本/参考/反面教材）
├── versions/       每次修改自动存档，可回滚
└── feedback/       人工修改 diff 归集，质量飞轮原料
```

```bash
python3 cli/avctl.py skill new writer 作家 --output story_file
python3 cli/avctl.py skill check           # 校验全部
```

强制章节：角色定义 / 职责边界 / 方法论 / 输入输出契约 / references调用方式。
职责边界章节必须写出明确禁区（否定表述），写不出「我不管什么」的 skill 一定会越权。

### 3. 模型网关（`core/gateway/`）

- Anthropic / DeepSeek 统一抽象，urllib 实现，零依赖
- 每个 skill 独立绑定模型与 temperature（作家可高温发散，分镜必须低温求稳）
- 重试、token 计费日志（`config/calls.jsonl`）、dry-run 占位模式
- JSON 输出容错：模型加了围栏或前言也能正确解析

### 4. 存储层（`core/store/`）

SQLite 存元数据，文件系统存产物正文 —— 产物必须人可读可手改，塞进数据库就废了。

目录约定即内容组织结构：

```
projects/<账号>/<合集>/<剧集>/
    _series/     角色板、场景板（全剧共享，跨集一致性在架构上锁死）
    ep01/        故事档案、剧本、分镜表
    assets/      回传的设计图与视频片段
```

每份产物落两个文件：`.json` 给下游 skill 机器消费，`.md` 给你在审核门里读和改。

数据库已建好血缘、引用申报、reference 健康度（引用次数 / 引用后大改率）三张表 ——
质量飞轮和 references 治理的数据底座 M0 就位，M5/M6 直接用。

## 设计决策备忘

**为什么零外部依赖**：单人碎片时间维护，每一个依赖都是未来某天环境炸掉的隐患。
M4 上界面才引入 Flask。

**为什么产物落两份文件**：审核门的核心能力是「你直接改文件」。
只有 JSON 你读着累，只有 Markdown 下游没法机器消费。

**为什么契约允许 extra 字段**：对应规划里「契约定得太早太死」这条风险。
只强校验核心字段，扩展字段自由添加，M2 发现不够用时不必推倒重来。

**为什么 dry-run 要做在 M0**：碎片时间开发最怕的是每改一行引擎逻辑就要花钱等模型返回。
占位产物字段齐全能过校验，引擎逻辑可以离线迭代。

## M1 交付了什么

### 作家 skill（`skills/writer/`）

方法论层题材无关，五步：先发散后收敛 / 一句话测试 / 情感落点必须落在人身上 /
钩子必须由故事长出来 / 人物只给功能不给外形。七条质量红线。

### 编剧 skill（`skills/playwright/`）

分场逻辑 + 动作-反应链 + 对白三条硬标准 + 信息释放设计 + 关键句三选一。
职责边界写死不碰镜头，且有校验器硬拦截。

### 题材模块机制（`skills/*/genres/`）

**为什么是模块不是独立 skill**：分成悬疑作家、喜剧作家、情感作家三个 skill，
方法论层就有三份拷贝，改一条红线要改三遍，漏改一处就开始漂移。
模块化则是方法论一份，题材模块每个一个薄文件，引擎按 genre_tags 命中加载。

**哪些 skill 该分题材**：只看一件事 —— 换个题材，它的判断标准变不变。

| skill | 题材维度 | 变异来源 |
|---|---|---|
| 作家 | 完整题材模块 | 题材 |
| 编剧 | 薄的对白语感模块 | 题材 + 导演 |
| 选角 / 场务 / 分镜 | 无 | 导演 |

下游 skill 不开题材维度，是因为它们的变异来源是导演。两边同时下指令会打架，
导演说慢节奏长镜头、题材模块说悬疑要快切，模型只能和稀泥。

已建模块（作家版 + 编剧对白语感版各一套）：

| 模块 | 作家版关注 | 编剧版关注 | 触发别名 |
|---|---|---|---|
| 情感 | 共情先于事件、克制而非加码 | 留白、关键情感禁止直说 | 亲情/家庭/催泪/爱情 |
| 悬疑 | 疑问分层、线索公平性 | 说漏而非告知、答非所问 | 推理/犯罪/反转/烧脑 |
| 喜剧 | 期待落差、人物必须认真 | 留响、落点在句尾 | 搞笑/幽默/沙雕 |
| 爽剧 | 憋气才是技术活 | 主角少说、对手多说 | 逆袭/打脸/复仇/扮猪吃虎 |
| 现实 | 内行才知道的细节层 | 不像台词、不说金句 | 社会/职场/生活流/纪实 |

多标签会同时命中多个模块（"职场"+"催泪" → 现实+情感）。
未覆盖的标签会显式提示"本次无模块支撑"，让你知道哪一次是在裸奔。

### 怎么加新题材

```bash
avctl genre new wuxia 武侠 --aliases 江湖 古装 侠客 仙侠
```

一条命令做三件事：给作家和编剧各生成一份模板、把别名同步登记到两个
`index.json`、别名立即生效。然后填模板内容，`avctl skill check` 验一遍即可。

不动 SKILL.md 正文，不动任何代码。

`avctl genre list` 查看当前所有模块、字数和别名。

**写模块的三条要求**（模板里也写了）：

1. **只写这个题材独有的**。方法论层已有的不要重复 —— 重复会让上下文里出现
   两份说法，冲突时模型不知道听谁的。
2. **蒸馏判断，不蒸馏知识**。模型已经知道教科书上的东西。写完每条自问：
   这一条模型自己想得到吗？想得到的删掉。
3. **判断标准必须可执行**。"人物要立体"没法执行；"把笑点换给另一个人物，
   效果一样就是外挂的"可以执行。

**作家版和编剧版分工**：作家版管结构和判断（1300-1500 字），
编剧版只管对白语感（600 字上下）。编剧版写长了会挤占上下文、稀释注意力。
如果某个题材的对白没有特殊语感，编剧版可以不建 —— 用
`--only writer` 只给作家建。

**什么时候该开新模块**：只看一件事 —— 换到这个题材，判断标准变不变。
写不出"这个题材的核心难题"，说明它还不值得单开一个模块。

### 审核门（`core/engine/gate.py`）

```bash
avctl review approve <产物.json>                        # 通过
avctl review revise  <产物.json> --before <生成版>       # 手改后通过
avctl review reject  <产物.json> --notes "修改意见"      # 打回重生成
```

`revise` 是质量飞轮的进料口：改动 diff 自动归集到对应 skill 的 `feedback/`，
改动比例超过 15% 记为大改，计入所引用 reference 的健康度。
`reject` 会把修改意见和被否产物一起拼成重生成用的任务说明。

### 跑一遍内容链路

```bash
avctl run writer --brief "你的主题" --series demo --episode 1 --genre 亲情
avctl review approve projects/default/s1/demo/ep01/story_file.json
avctl run playwright --input projects/default/s1/demo/ep01/story_file.json \
    --series demo --episode 1
```

题材标签缺省时自动从上游产物的 genre_tags 继承。

## M2 交付了什么

### 选角 skill（`skills/casting/`）

核心是**锚定描述**——一段专门写来对抗生成随机性的文字。必须覆盖脸型骨相、
五官形状、发质肤色、年龄的具体表现、体态六个维度，且必须"可测量"不能"评价性"：
"帅气清秀"每个模型理解都不一样等于没写，"眉骨突出、鼻梁挺直但鼻头圆钝、
嘴角自然下垂"才是坐标。

外加 1-2 个标志性记忆点当保险丝：锚定再细脸也会浮动，即使漂移 20%，
观众靠那道疤仍认得出是同一个人。

### 场务 skill（`skills/set_dresser/`）

与选角同构，对抗的是**布局漂移**。核心要求是方位必须写死——
不能只说"有一扇窗"，要说"窗在灶台正对面那面墙上"，方位模糊每次生成都会重排。

另一条是**使用痕迹**：新手容易把场景写成样板间，好看但没人味。
三到五处具体痕迹（抽屉关不严、灶台边常年油渍）既给真实感，
也在讲住这里的人是什么人。

### 分镜 skill（`skills/storyboard/`）

全平台提示词密度最高的一环，核心纪律是**引用不描述**：
提示词里的人和景必须取角色板场景板的锚定描述原文，不能"理解了然后用自己的话写一遍"——
每个镜头的"自己的话"都不一样，几十个镜头就是几十张脸。

分镜刻意不开题材模块。镜头语言随题材变化很大，但**变化来源应该是导演不是题材**。
两边同时下指令会打架，模型只能和稀泥。

### 必需上游执法

```bash
avctl run storyboard --input 只给了剧本.json ...
✗ 缺少必需的上游产物，拒绝执行：
    - character_board（角色板），由 casting 产出
    - location_board（场景板），由 set_dresser 产出
```

**为什么要有这道拦截**：缺上游的产物表面能跑通，实际是在裸奔。
分镜没有角色板时会自己发明人物长相，而引用完整性校验恰好因为缺上下文被跳过——
最该生效的时候失效。M2 开发过程中实测复现了这个漏洞，补上了。

`manifest.required_inputs` 可以细调，缺省视为全部 input_contracts 必需。

### 流水线看板

```bash
avctl pipeline --series demo --episode 1
```

五个节点的状态一目了然，并指出当前卡点。剧集级（角色板/场景板）与
集级（故事/剧本/分镜）分开标注。

### 跑一遍完整链路

```bash
D=projects/default/s1/demo
avctl run writer     --brief "你的主题" --series demo --episode 1 --genre 爽剧
avctl run playwright --input $D/ep01/story_file.json --series demo --episode 1
# N4/N5 可并行
avctl run casting     --input $D/ep01/screenplay.json --series demo
avctl run set_dresser --input $D/ep01/screenplay.json --series demo
avctl run storyboard  --input $D/ep01/screenplay.json \
    $D/_series/character_board.json $D/_series/location_board.json \
    --series demo --episode 1
```

## M3 交付了什么

### 导演层（`skills/directors/`）

导演**不是流水线节点**，是注入到每次 skill 调用里的风格约束层。
同一个编剧 skill 在不同导演下产出完全不同的剧本，而 skill 本身保持通用。

导演走**另一套规范**（不是工种 skill 的五章节）：
擅长题材 / 叙事偏好 / 镜头语言 / 对白风格 / **禁忌清单**。

禁忌清单是最重要的一节，校验器会检查它是否有实质内容——
说不出「我绝不这么拍」的导演等于没有风格，注入下去产生不了可分辨的差异，盲测必然失败。

已建三位：

| 导演 | 一句话 | 标志性禁忌 |
|---|---|---|
| 贾樟柯 | 把人放回时代里，让环境和时间替人说话 | 绝不解释时代背景、绝不给人物英雄时刻、绝不闭合结局 |
| 王家卫 | 所有人都在错过，所有话都说不出口 | 绝不让关键的相遇真正完成、绝不说破关系、绝不用自然光 |
| 邵氏 | 恩怨分明，招招见血，一场戏交代一件事 | 绝不把动作剪碎、绝不做心理写实、绝不用暧昧结局 |

三份文档写的都是**风格机制**（镜头、节奏、对白处理），
每份开头有硬护栏：禁止复制具体影片的情节、场面、台词、人物设定。
这与平台原有的 references 护栏一致——学怎么拍，不学拍什么。

三者的对白路线完全分岔（方言口语 / 独白诗化 / 文白工整），
盲测的可分辨性主要靠这一层。

**一个刻意的例外：作家不吃导演上下文。** 导演是根据故事题材选的——
故事在前，导演在后。让作家吃导演等于倒因为果。引擎会自动豁免并提示。

```bash
avctl director list
avctl director match --input <故事档案.json>   # 匹配器：推荐+理由，你拍板
avctl director new <id> <名字> --genre ... --one-line "..."
avctl run playwright --director jiazhangke --input ... 
```

### 盲测工具（M3 的验收方式）

```bash
avctl blindtest playwright --directors lengxu jifeng \
    --input <故事档案.json> --out blindtest
```

同一份输入跑两个导演，产出**去标识、随机打乱**的对照文件，答案封在 `_答案.txt`。

**验收标准**：你看两份产物能分辨出哪份是哪个导演的，风格注入才算立住。
分不出来说明这条路没走通，应当停下来重新设计注入方式，而不是硬着头皮做 M4。
这是整个规划里唯一设了「不通过就停」的关卡。

## M5（部分）交付了什么

### 拉片员 skill（`skills/film_analyst/`）

不在流水线上，是**进料泵**——把片子拆成 skill 能消化的养料。

核心是**双层结构**：观察层记实例（简短，仅作佐证），
抽象层记机制（主力）。只有观察层的笔记是毒药——skill 读到实例只会模仿具体场面。

外加**适用条件与失效条件**两栏，这是整份笔记最值钱、也是绝大多数拉片笔记里没有的部分。
没有它们，skill 会在错误的场合套用正确的机制。

一部片拆**三份分流笔记**（编剧向/选角向/分镜向），因为消费者不同。
一份大杂烩塞进三个 skill，等于每个都吃进三分之二噪音。

四维标签：题材 / **结构位置** / 情感目标 / 载体约束。第二维最常被漏、检索时最有用。

### 抽帧工具链（`tools/ripfilm.py`）

```bash
python3 tools/ripfilm.py 片子.mp4 --out ripdata/xxx
```

按**转场检测**抽关键帧（不是均匀抽——均匀抽会漏掉快切段落）、
提取字幕轨、生成镜头时长分布统计（分镜向笔记直接消费这份数据：
平均单镜时长、2 秒内占比、8 秒以上占比）。

手工拉片几小时压到十几分钟。需自行安装 ffmpeg。

## M4 交付了什么

### 生产工作台

```bash
pip install flask --break-system-packages
python3 web/app.py          # http://127.0.0.1:5001
```

页面：剧集总览 / 流水线看板 / 产物审核门 / Skill 管理 / 导演库。

**视觉方向：通告单 / 场记板。** 审核门在真实剧组里就是盖章，
所以通过的节点盖一枚旋转的红印章——这是整个界面的签名元素。
冷灰蓝纸底 + 墨黑 + 单一印章红，纸纹用极淡的横向条纹。

**两个刻意的信息编码**：

1. **卡点与等待分开。** 当前卡住的节点用琥珀色，卡点之后的节点静默处理。
   否则一眼看过去五个节点全在报警，反而看不出真正该动的是哪个。
2. **审核门先读后改。** 页面顺序是 引用申报 → 审阅版 → 动作 → 直接修改。
   审核的本职是读和判断，编辑是次要动作，把 JSON 编辑框放在最前面是本末倒置。

**审核门在界面上的三个动作**与命令行完全一致：盖章通过 / 保存修改 / 打回重做。
保存修改会校验契约（不通过则拒绝保存并列出具体字段）、
把 diff 归集到 skill 的 feedback、改动超 15% 记为大改。
打回必须写修改意见，否则拒绝——没有意见，重生成时模型不知道错在哪。

Skill 详情页可在线编辑 SKILL.md（保存自动存档旧版），
并展示题材模块、reference 健康度（引用次数 / 引用后大改率）、人工修改反馈数量。

## M6 交付了什么

### 质量飞轮闭环

```bash
avctl flywheel status              # 全部 skill 的飞轮状态
avctl flywheel analyze writer      # 修改模式分析
avctl flywheel suggest writer      # 生成改进建议（需 ≥5 条反馈）
avctl flywheel review writer       # 查看待批建议
avctl flywheel apply writer --pick 1 3   # 合入选中项
avctl flywheel apply writer --reject     # 全部驳回
```

**模式分析**统计高频被改字段、按 skill 版本分布、**按导演分布**。
最后一项很关键：若修改集中在某一个导演下，问题可能出在导演约束
而非 skill 本体，改错地方会越改越糟。

**五条样本门槛**：少于 5 条反馈拒绝生成建议，样本太少会把偶然当规律。

**三道合入保护**（skill 是这个平台唯一的资产）：

1. 替换必须精确匹配原文，找不到就报错，**绝不模糊匹配**——改错地方在 diff 里看不出来
2. 原文在文件中出现多次时拒绝替换
3. 合入后立即复检规范，不合规**自动回滚**到上一版

实测：一条会删掉整个「职责边界」章节的建议被合入后立即检测并还原。

**永不全自动合入。** 一次错误的自动合入会污染之后所有产出，
且很难回溯到哪一版开始变坏的。

### reference 治理

- **闲置**：从未被引用 → 标签打错了，留着拖慢检索精度
- **误导**：引用够 5 次且引用后大改率 ≥60% → 这条在误导模型，比没有更糟

### 成片数据回流

`record_performance()` 把发布后的数据（播放、完播率、互动）标注回产物。
价值要等样本攒够才显现，但采集必须从第一条片子就开始——补采是补不回来的。

## 把 skill 拿出去单独用

```bash
python3 cli/avctl.py export            # 三种格式全出
python3 cli/avctl.py export --format claude
```

平台真正的资产是 skill，平台只是编排它们的壳子。所以 skill 必须能单独拿走。

导出的难点在于**平台运行时会往上下文注入四样东西**（导演约束、题材模块、
契约字段规格、references），脱离平台后没有引擎做这件事，
所以导出的 SKILL.md 必须自带这些，否则拿出去就是残缺提示词。

| 格式 | 目标 | 处理方式 |
|---|---|---|
| `claude` | Claude Code 的 `.claude/skills/` | 带 YAML frontmatter，题材/导演作为附属文件随包带走 |
| `codex` | Codex / 通用 agent | 单文件自包含，题材与导演全部内嵌 |
| `plain` | 任意对话框 | 纯 Markdown，复制即用 |

**导出规则跟平台的架构一致**：作家带题材不带导演（故事在前导演在后），
编剧两者都带，选角/场务/分镜只带导演（它们不开题材维度），
拉片员两者都不带（不在流水线上）。

**导出版没有契约校验器**——平台里编剧写了镜头会被强制打回，
导出版只有文字约定。要严格执法还是用平台。

**M1（内容质量）**：跑真模型产出故事档案和剧本，你读完认为「值得往下做」。
包里 `_testcase/` 有一份按同一份 SKILL.md 手写的完整产出可先参考。

**M2（一致性）**：角色板提示词去图像模型跑，同一角色五张图长相一致；
分镜提示词去视频模型跑，画面里的人和景与上游对得上。
这一关最要紧——一致性是流水线最贵的返工点。

**M3（风格分辨）**：跑一次 blindtest，看能不能分辨出哪份是哪个导演的。

三项都是代码之外的验收，`avctl smoke` 只能验到机制通不通。
建议一次跑完三项，省时间。

每次改动前先 `snapshot` 存档，可回滚。
